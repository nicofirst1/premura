# The MCP tool surface exposes parameterized tools, not one tool per instance

> **Status:** Accepted — 2026-08-10

The default agent surface had grown to ~35 tools, of which ~19 were per-instance enumerations: eight grounded signals each got their own tool (`resting_hr_status`, `steps_trend`, `weight_trend`, …), the three descriptive single-metric analytical tools stood separately (`change_point`, `smoothed_average`, `rolling_mean`), the two paired-difference tools stood separately (`paired_t_test`, `condition_paired_t_test`), and condition-episode capture was three verbs (`record` / `list` / `retract`). This is the pattern [DOCTRINE.md](../../shared/DOCTRINE.md) bans — hardcoding a list where the rule for adding to the list belongs — and a wide near-duplicate menu degrades a model's tool selection. This note records the collapse so later tools extend the parameterized surface instead of re-adding per-instance tools.

The decisions:

- **Enumerations collapse into one parameterized tool; distinct capabilities do not.** The eight signals become one `signal(name, params)` tool whose no-argument call returns a self-describing catalog; the three descriptive single-metric methods become `analyze(method, …)`; the two paired differences become `paired_test(kind, …)`; record/list/retract become `condition_episode(op, …)`. Tools that are _not_ per-instance enumerations stay separate: `correlate` (a distinct two-metric hypothesis shape), `interview_route` vs `interview_devices` (different questions over different registries, and `interview_devices` already dual-modes internally), and the governance/trace/orchestration tools. The self-check is the DOCTRINE one — is this a list of instances of one rule (collapse), or genuinely different jobs (keep)?

- **A descriptive pattern and a pre-registered hypothesis test must not share one menu slot.** `analyze` carries only the three descriptive single-metric methods; the pre-registered paired hypothesis tests live in `paired_test`, and the pre-registered lagged association stays its own `correlate` tool. Lumping a t-test under the same selector as a smoothing function would invite an agent to treat them as interchangeable — the exact epistemic sloppiness the trace/disclosure discipline ([ADR 0009](0009-session-research-trace-and-multiplicity-disclosure.md)) exists to prevent.

- **The collapse is at the MCP surface only; nothing below it moves.** Each parameterized tool reconstructs the identical downstream call the former per-instance tool made — the same engine/store call, and for analytical tools the same `tool_name` and request handed to the trace. So the engine stays byte-identical, the normalized hypothesis identities and the measured multiplicity of ADR 0009 are unchanged (the trace still records `change_point` / `paired_t_test` / `condition_paired_t_test`), and every per-signal window bound and the HRV explicit-anchor path are preserved. The default surface goes from ~35 tools to 23.

Consequences: adding a new grounded signal is a registry entry plus one catalog/dispatch row in the MCP layer — the agent still sees exactly one `signal` tool, never a growing menu. The authoritative tool inventory remains the test-suite assertion (`tests/mcp/test_mcp_server.py`); the four selectors (`signal` name, `analyze` method, `paired_test` kind, `condition_episode` op) are the seams new work plugs into by declaration rather than by adding a top-level tool.
